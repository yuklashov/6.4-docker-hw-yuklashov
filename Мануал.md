Образ Go соответствует официально полученному локальному инструменту. GitLab CI ещё не запускался: локальная проверка Go не заменяет pipeline.

## Что осталось

1. Получить доступный Linux-стенд. На Mac не найдены рабочие Docker/Vagrant/Go; Go скачан отдельно во временную папку с проверкой SHA256. VBoxManage list vms завис без результата, существующая VM не подтверждена. Исходный Vagrantfile рассчитан на ubuntu/bionic64 и 6144 МБ RAM; текущий Mac — ARM64 с 8 ГБ RAM. Не запускать исходный x86-стенд вслепую.
2. Развернуть GitLab и зарегистрировать project runner с Docker executor и тегом docker. Для данного Go pipeline не нужны privileged=true и проброс Docker socket в job.
3. В отдельной рабочей копии учебного проекта сохранить GitHub remote как github, назначить origin адресом созданного GitLab-проекта и выполнить push. Не менять origin существующего sdvps-materials.
4. Проверить в GitLab: начальный push с Go-файлами — test+build; следующий push только README — build; следующий push main.go — test+build. У build отсутствует зависимость от test, но фактическая параллельность требует двух доступных слотов раннера.
5. Сохранить реальные снимки runner online, executor docker и pipeline passed, скрыв токены. Указать версии GitLab/Runner и ссылку на проект. Отправить готовую ссылку в LMS и проверить подтверждение отправки.

rules:changes в новом branch pipeline трактует весь исходный набор как изменения; это даёт начальную проверку проекта. workflow исключает tag, schedule, web и MR pipelines, для которых сравнение изменений требует отдельной политики. Последующие push сравниваются с предыдущим коммитом.

Официальные пояснения: https://docs.gitlab.com/ci/yaml/needs/ и https://docs.gitlab.com/ci/jobs/job_rules/.
