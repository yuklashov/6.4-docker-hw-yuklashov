## Задание 2 — репозиторий и pipeline

Подготовлены [исходный код](main.go), [тесты](main_test.go), [модуль Go](go.mod) и [.gitlab-ci.yml](.gitlab-ci.yml). Приложение основано на Go-примере из учебного репозитория [netology-code/sdvps-materials](https://github.com/netology-code/sdvps-materials).

Pipeline выполняется при push в ветку. Docker Runner использует образ `golang:1.27.3`. Job `test` проверяет форматирование, выполняет `go vet` и `go test`. Job `build` собирает Linux-приложение, проверяет его запуск и сохраняет бинарный файл `dist/hello` как артефакт на 7 дней. Привилегированный контейнер и Docker socket для этих jobs не требуются.

[Локальные проверки](evidence/local-checks.txt) выполняются отдельно от GitLab. Успешный pipeline в GitLab и перенос origin пока не выполнены; соответствующих скриншотов нет.

## Задание 3* — независимая сборка и выборочный запуск тестов

В `build` задано `needs: []`: job готова к запуску сразу, не ожидая завершения `test`. Параллельное выполнение возможно при двух доступных слотах раннера.

В `test` используется `rules:changes` с шаблонами `*.go` и `**/*.go`. На последующих push только документации тестовая job пропускается, сборка остаётся. Первый push новой ветки запускает начальную проверку; tag, web, schedule и MR pipelines исключены через `workflow:rules`.

Синтаксис основан на [GitLab needs](https://docs.gitlab.com/ci/yaml/needs/) и [rules:changes](https://docs.gitlab.com/ci/jobs/job_rules/). Исполнение этого поведения на настоящем GitLab ещё предстоит проверить.
